Distributed Agent System

Three agents. Three frameworks. One protocol.

A user pastes a meeting transcript. One agent discovers another through the A2A protocol, delegates the analysis, and the structured output is handed to a third agent that drafts follow-ups. Each service runs on a different agent framework. They share no code — only a JSON-RPC contract and an agent card published at a well-known URL.

How it fits together

One round-trip, three services, two protocols, two hops.

User pastes a transcript
HTTPS→
meeting-chat Google ADK · LiteLLM
A2A⇄
meeting-processor OpenAI Agents SDK
REST→
meeting-followup LangGraph · Postgres

The chat agent fetches /.well-known/agent-card.json to discover the processor, then sends tasks over JSON-RPC 1.0. Structured output (action items, owners, due dates, source quotes) is returned to the caller, which passes it to POST /workflows on the followup service — the LangGraph engine drafts a follow-up message per action item and returns the drafts for approval.

Under the hood

The A2A round-trip, as it appears in the logs.

  1. 1 GET /.well-known/agent-card.json → 200 chat discovers the processor
  2. 2 POST / (SendMessage) → 202 transcript delegated over A2A
  3. 3 POST / (task completed) → 200 MeetingAnalysis returned
  4. 4 [tool] analyse_meeting_a2a(N chars) chat formats the response
  5. 5 POST /workflows (action items) → 200 LangGraph drafts follow-ups

Semantic retrieval, not keyword matching

The query and the stored content share no keywords.

Query "What did we decide about ad spend?"
Stored "…increase marketing spend by 20 percent…"

Zero shared keywords. Retrieval is via pgvector cosine similarity against text-embedding-3-small vectors. The agent returned the correct decision, the owner, the due date, and the source quote.

Honest limits

What's shipped, and what's deferred.

  • Cold start — the free tier sleeps after 15 minutes idle. The page warms all three services in parallel on load and shows a status pill; the first request may still take ~60s if the pill hasn't turned green.
  • Two-step flow — Step 1 (analysis) and Step 2 (drafting) are separate API calls. The two hops are a deliberate service interface, not an inline chain. Full chaining requires an async checkpointer migration in meeting-followup.
  • In-memory A2A task store — the processor uses InMemoryTaskStore, so task state is lost on restart. A DatabaseTaskStore is the follow-up.
  • Decision over-extraction — measured precision 0.17–0.35 across 5 hand-labelled transcripts. Documented rather than tuned away; the eval harness lives in meeting-processor/evals/.
